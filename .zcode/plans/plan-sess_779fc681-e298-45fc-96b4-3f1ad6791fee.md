# 动伴语音链路改造方案

## 一、先回答你的问题（现状真相）

**你现在用的模型（4 个角色）：**
| 角色 | 模型 | 说明 |
|---|---|---|
| 文本对话 | `qwen3.5-plus` | 走 openai-next 中转，temperature 0.5 / max_tokens 140 / 已关思考模式 |
| 视觉 | `qwen3-vl-flash` | **只有说"看看画面"才调用**，单帧 360px JPEG |
| 语音合成 | `qwen3-tts-flash`（Serena 音色） | 整段合成、整段下载后才播放 |
| 语音识别 | 浏览器原生 Web Speech API | **不是自选模型**，Chrome 底层是谷歌云识别，断句急、延迟不可控 |

**交互逻辑 = 轮次式对讲机**：唤醒 → 你说一句 → **麦克风直接 abort() 关闭** → 等 LLM 把 45 字全部生成完（非流式）→ 等 TTS 把整段 mp3 合成并下载完（非流式）→ 播放 → 播完 → 220ms 后重开麦克风。README 实测 3.05 秒。

**延迟高的根因（不是模型笨）**：三段串行 + 每段都等 100% 完成。`enable_thinking` 早关了，慢在管线：LLM 首字其实很快，但你必须等它最后一个字生成完；TTS 同理。

**打断不了**：播放期代码里主动 `recognition.abort()`，全项目没有一行 barge-in 逻辑。是设计如此，不是模型能力问题。

**"训练完成辛苦了"假**：`Summary.tsx` 第 15 行硬编码字符串，而且用的是 `window.speechSynthesis`（**系统机械音，连 Serena 都不是**）+ 文案不看任何训练数据。假人感 = 死文案 + 换了音色。

## 二、参考项目（"贾维斯"类）

- **OpenAvatarChat**（阿里 HumanAIGC）— 最像贾维斯：SenseVoice+Qwen+CosyVoice 全链路+数字人，但需要 GPU
- **TEN Framework**（声网）— 打断/轮次检测最成熟，云服务可无 GPU
- **pipecat**（Daily.co）— Python 语音 agent 框架，"分句流水线 + VAD 打断"的标准实现，本次架构主要参考它
- **LiveKit Agents** — RTC 语音 agent，打断原生支持
- 自托管路线备选：FunASR（SenseVoice ASR）+ CosyVoice（开源流式 TTS）

**结论：不用换模型。** qwen3.5-plus 和 qwen3-tts-flash 都够用——已查证 qwen3-tts-flash 支持 SSE 流式（`X-DashScope-SSE: enable`，Base64 PCM 逐段返回）。慢和假是架构问题。

## 三、实施内容（4 个阶段，每步独立可验证）

### 阶段 1：流式对话管线（首响 ~3s → ~1s）
- 服务端新增 `POST /api/companion/chat/stream`（SSE）：LLM 调用改 `stream: true`，按终止标点切句，每凑齐一句 → 立即对该句调 qwen3-tts-flash 流式合成 → 把"句子文本 + 音频 PCM 块"事件转发给前端
- 前端播放从 `<audio>` mp3 改为 **Web Audio 队列**（AudioContext，24kHz PCM 按序无缝播放），第一句到就出声
- 旧非流式端点保留做 fallback
- 顺带：chat 加最近 3 轮对话历史（现在是无记忆单轮，这也是"像假人"的一部分）

### 阶段 2：可打断（barge-in）
- 播放期不再关麦：单独 getUserMedia 一路 `echoCancellation:true` 的流，AudioContext AnalyserNode 做能量 VAD
- 检测到用户开口 → 立即停播 + 清空未播句队列 + 回到监听态；能量阈值 + 防抖防自己声音误触发

### 阶段 3：结束语和个性（去假人味）
- 删 Summary.tsx 的系统 TTS 硬编码；进入总结页时把本次数据（次数、时长、心率、XP、连续天数、称呼、鼓励风格）发给服务端生成一句 ≤30 字的针对性口语总结，流式 Serena 播放（"20 个深蹲一个没落"这种，不再"辛苦了"）
- system_prompt 强化三种鼓励风格的具体口吻示例，让日常对话少 AI 腔；安全边界（apply_response_policy）不动

### 阶段 4：流式 ASR 换引擎
- 服务端新增 WebSocket 代理 `/ws/asr`（`server/asr_proxy.py`）：前端 AudioWorklet 采集 16kHz 单声道 PCM → 服务端转发 DashScope paraformer 实时识别（已查证：`wss://…/api-ws/v1/inference`，run-task → 音频流 → result-generated 增量返回 → finish-task；key 只在服务端）→ 中间结果实时回传前端
- 中间结果实时做唤醒词匹配 + 静默 600ms 定稿；浏览器 SpeechRecognition 保留为降级路径
- 协议细节 JSON 字段实装时按官方"客户端事件/服务端事件"子页核对（已定位到文档 URL）

## 四、文件改动
- `server/app.py`：流式端点、切句、TTS 流式、prompt 强化、多轮历史
- `server/asr_proxy.py`（新）+ `requirements.txt` 加 `websockets`
- `src/hooks/useVoiceCompanion.ts`：流式消费、Web Audio 队列、barge-in、ASR WS 客户端（大改）
- `src/services/companionApi.ts`：SSE 解析方法
- `src/pages/Summary.tsx`、`Workout.tsx`：结束语、session 数据接入
- `.env.example`、`server/test_app.py`：新配置与切句/prompt 测试

## 五、验证
每阶段跑 `pnpm run test:core` + `pnpm run test:server` + `pnpm build`；最后真机实测：从说完到出声的延迟计时、打断实测、结束语试听。不通过不说好了。
